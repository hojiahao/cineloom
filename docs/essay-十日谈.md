# 十日谈：在一台 DGX Spark 上，把一句创意织成一支广告片

> 第三届 NVIDIA DGX Spark 黑客松 · Agent Skills 开发挑战赛 · 方舟团队
> 项目：CineLoom（影织） · 仓库：https://github.com/hojiahao/cineloom

## 一、为什么做这个

做一条 15 秒的短视频广告，要过策划、文案、合规、分镜、拍摄、剪辑六道工序。AI 视频工具把“拍摄”这一道变便宜了，却带来三个新问题：

- **素材不能上云。** 未发布的新品、内部设计稿，交给云端视频工具就等于提前曝光。
- **返工按次计费。** 一个镜头重生成五次是常态，每次都是一笔钱，试错就变得很贵。
- **没人把关。** 一句“全网第一”、一个变形的 logo、一行错字，往往到成片才发现，而这时前面的算力已经花掉了。

DGX Spark 有 121.7 GB 统一内存，第一次让“语言模型、视觉模型、图像模型、视频模型放在同一台机器上”成为现实。我们想回答一个问题：在一台桌面上的机器里，能不能让一组智能体像一个小型广告工作室那样工作，从一句创意出发，交付一支字幕正确、文案合规、产品前后一致的成片？

## 二、我们做了什么

CineLoom 的核心是自研的运行时 **CineLoom Harness**。它把一支片子拆成八个阶段：需求、脚本、合规、分镜、生图、质检、生视频、成片。顺序由代码保证，每个阶段交给一个加载了对应 **Agent Skill** 的子智能体。

我们给它定了一条原则：**代码管顺序和验收，模型管判断。** 每个子智能体交出的东西，先过一道确定性校验器，比如节拍数、字数、镜头数、广告法用词、画面里是否要求画字。不合格就带着具体问题退回重写，而不是“再试一次”。九个 Skill 把每个环节的专业判断写成了可复用、可评测的文本：怎么写脚本、怎么审合规、怎么做分镜、质检不过时怎么改提示词、这台 Spark 的内存怎么排。

模型分工按实测来定，不按想象：

- **NVIDIA Nemotron 3.5 Lightning**（NVFP4，配 DGX Spark 专用的 DSpark 投机解码）负责需求、文案、审稿和英文提示词，本机实测每秒约 100 个 token。
- **StepFun Step3-VL-10B** 负责看图质检：每一帧都对照产品定妆图复核。
- **StepFun Step-Audio-EditX** 负责配音：克隆参考音色后，再按广告腔重新演绎。
- **Qwen-Image / Qwen-Image-Edit** 出图，**Wan2.2 14B** 出视频，**ACE-Step** 出配乐，全部在 ComfyUI 里本地运行。
- 云端只做可选增强：TypeSafe 的 Jev 给文案和分镜做校准概率判读，每个素材都标注了是本地生成还是云端生成。

最后交付的是四个行业的四支样片：饮料、数码、护肤、食品，竖版和横版都有。每支片子都附带一份自动生成的交付报告，逐镜头写明质检了几次、为什么被拒、耗时多少。

## 三、十天里做对的几个决定

**先出定妆图，再出每一帧。** 第一支片子里，罐子在镜头一是铝罐，到镜头二变成了瓶子。之后的做法是：先生成一张产品定妆图，由视觉模型确认它就是这个产品，此后每一帧都以它为参考图生成。整支片子里是同一只罐，同一个“冷”字。

**画面里不让模型写字。** 图像模型会把“50mm”画进画面，会把“泠”画成“冷”。所以标题和字幕一律在后期用真字体排版，并检查字体是否缺字；图像提示词里只允许出现产品本身印着的品牌字。

**返工拦在最便宜的阶段。** 生一张首帧约 60 秒，生一段 5 秒视频约 350 秒。所以每一帧先过质检再生视频，不合格就改提示词重生成。气泡水那支里，镜头一两个候选都因“罐子没立稳”被拒，第三个候选通过后才进入视频阶段。

**用户说了的，不交给模型重新决定。** 创意原话写着“横版”，需求智能体选了竖版；写着“银色铝罐”，分镜智能体编了个玻璃瓶。修法不是再教模型，而是让代码把原话里的画幅、时长和外观逐字保留下来，由校验器对照检查。

## 四、十天里踩过的坑

**模型把 Skill 里的示例抄了过来。** 面霜那支片子，分镜智能体把 Skill 文档里的示例产品（一罐气泡水）原样搬了过来，定妆图质检连续三次拒绝，理由是“标签是冷，不是润”，系统却带着错误的产品把片子做完了。修了三处：分镜必须写出本创意的品牌字，定妆图三次不过就停止，Skill 里的示例改成不可照抄的占位写法。几天后，脚本智能体又把示例里的标题“开罐”抄给了挂耳咖啡，于是又加了一条规则：标题里提到的容器必须和产品相符。

**3C 产品最难。** 机械键盘做了五版。第一版三个镜头几乎是同一个角度，六十个键帽字全是乱码，还有没人要的彩虹底光。之后每一版修掉旧问题，又冒出新问题：手出现在每个镜头里，键盘在定妆图里被立起来，分镜里写了一句“黄铜质感”键盘就变成了金色，视频模型还会自己叠出一把半透明的“幽灵键盘”。我们没有换模型，而是照着真实的 3C 广告拍法，把每一次翻车写成分镜 Skill 里的“品类拍法”和校验器里的一条硬规则：单一冷色光、最多一个手镜头、不俯拍打字、键帽字虚化、分镜不得重新描述产品外观、视频负面提示词禁止彩虹循环和叠影。第五版进了 README。

**校验太松会带病前进，太严会原地打转。** 一开始校验不过时系统会带着问题继续跑；改成“明确失败”之后，又有两支片子卡在同一条规则上四次不过。最后的做法是给六次机会，最后两次打开 Nemotron 的思考模式，并把上一稿连同问题一起发回去，让它“改”，而不是“从头写”。一个被同一条规则退回三次的小模型，需要的是思考，不是第四次被告知。

**两条提速的路走不通。** 一支片子四十分钟太长。第一个猜想是内存挤占：两个语言模型常驻，视频模型每段都要重新搬权重。我们让语言模型在生视频时进入 vLLM 的睡眠模式，可用内存从 47 GB 翻到 104 GB，视频每段却一秒没少，语言模型反而慢了十倍，唤醒后不重载权重还会复读“后汉书后汉书”。第二个猜想是让视觉模型跳过推理直接判图，3 秒就出结果，但它开始把合格的帧判成不合格，理由是编的。两条路都回退了，也都如实写进了 README。真正有用的是首帧段的四项小改动：按视频尺寸出图、第二个候选只在第一个被拒时才生成、缩图送审、审图与生图流水化。首帧段从 1141 秒降到 524 秒。

**GB10 上的环境细节。** Docker 要用 CDI 暴露 GPU，`runtime: nvidia` 会直接报错；Step3-VL 的 FP8 权重要关掉 DeepGEMM；`docker stats` 看不到统一内存里的 CUDA 占用，内存一律以 `/proc/meminfo` 为准；Step-Audio-EditX 在新版 vLLM 和 transformers 上需要两处补丁（注意力后端、chat 模板返回值）。这些都写进了部署配置和 `spark-model-scheduler` 这个 Skill。

## 五、数字

**Skill 有没有用。** 同一个 Nemotron、同一批 8 个创意各跑 2 轮，唯一变量是子智能体有没有加载 Skill，每个阶段只给一次机会，用 Harness 自己的校验器计分。三次评测结果全部保留：

| | 第一次：不带 → 带 Skill | 第三次：不带 → 带 Skill |
|---|---|---|
| 脚本一次合格 | 0/16 → 6/16 | 11/16 → 14/16 |
| 分镜一次合格 | 0/16 → 8/14 | 0/15 → 6/15 |
| 分镜平均违规 | 8.00 → 0.71 | 3.80 → 0.80 |

第二、三次的“不带 Skill”基线明显变好，因为我们把节拍数、字数这类硬约束直接写进了阶段提示词。这是我们愿意写出来的结论：能写进提示词的确定性规则就该写进提示词，Skill 留给需要判断的部分；而分镜恰恰是判断最多的环节，差距依然明显。

**一支片子要多久。** 四支样片在本机分别用了 2256 秒（气泡水）、2432 秒（键盘第五版）、4564 秒（面霜，与另一任务并发）、3645 秒（咖啡）。首帧段提速后，同一条气泡水创意最快 1842 秒，比基线少 18%。视频三段约 1060 秒，这是 Wan2.2 14B 在 720p 下实打实的计算，不降规格就降不下来。

## 六、还没做完的

- 视频段的提速：480p 草稿模式加 720p 定稿，或者每段缩短到 4 秒，都会改变成片，我们还没有采用。
- 一个镜头返工两次，就能把首帧段省下的时间吃回去。下一步要让分镜智能体提前避开图像模型画不出来的东西。
- 音效层，以及更多品类的“拍法”。

十天里，每一次翻车都变成了 Skill 里的一条规则，或者校验器里的一行代码。这也许就是 Agent Skills 最朴素的价值：它让一个团队的经验可以被写下来、被评测，也能被下一个智能体继承。

— 方舟团队
